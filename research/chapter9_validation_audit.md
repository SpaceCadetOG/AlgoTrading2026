# Chapter 9 Validation Audit

Scope: audit only. No strategy logic, Chapter 10 code, ML, live trading, paper trading, or exchange calls were added.

## Summary

The event-driven backtester is currently useful as a **system-flow validation harness**, not as a realistic strategy-performance estimator.

The large `pnlDiff`, including the earlier reported `2252.38`, is expected from the current assumptions. The exact value changes between runs because `cmd/main.go` fetches a rolling latest candle window, but the cause is structural:

- the for-loop backtester uses candle signals, candle-close fills, fees, and slippage;
- the event-driven backtester creates deterministic crossed-book liquidity;
- the Chapter 7 test strategy buys at the best ask and sells at the best bid whenever `bestBid > bestAsk`;
- the simulator fills every accepted order at its submitted price.

Latest generated comparison observed:

```text
for_loop_final_equity=9999.74
event_driven_final_pnl=3381.12
pnl_difference=3381.38
event_driven_orders=16
event_driven_fills=16
```

## Findings

### Why `pnlDiff` Is Large

Severity: high

The two engines are not testing the same trading assumption.

The for-loop backtester is signal-driven. It opens/closes based on signal output and simulates fills from candle closes with venue fee/slippage models.

The event-driven backtester is crossed-book driven. In `backtest/event_driven.go`, `publishCrossedBook` creates:

```text
ask = close - spread / 2
bid = close + spread / 2
```

That means every generated book snapshot can contain a built-in arbitrage. The Chapter 7 `TradingStrategy` sees `bestBid > bestAsk`, buys the ask, sells the bid, and captures the spread.

Conclusion: the event-driven PnL is artificial and should not be compared as strategy alpha.

### Event-Driven Fills Are Not Realistic

Severity: high

`MarketSimulator.FillAllOrders()` fills every accepted order unconditionally. There is no:

- fee model;
- slippage model;
- latency;
- queue position;
- partial fill;
- fill ratio;
- market impact;
- one-leg fill risk.

This is fine for validating the Chapter 7 queue and OMS path. It is not realistic enough for deployment-quality backtesting.

### Crossed-Book Simulation Creates Artificial Profit

Severity: high

Yes. The current event-driven liquidity source creates artificial profit by construction.

The generated best bid is above the generated best ask. The strategy is specifically designed to capture crossed-book spread. Therefore, positive PnL mainly proves:

```text
LiquidityProvider -> OrderBook -> TradingStrategy -> OrderManager -> MarketSimulator -> OrderManager -> TradingStrategy
```

works mechanically.

It does not prove the strategy would make money in a live market.

### Order Book Carries Stale Liquidity

Severity: high

`system.OrderBook` appends and sorts bids/asks. It does not remove liquidity when strategy orders are filled.

The market simulator fills the strategy order, not the resting book liquidity that created the signal. So historical candle replay repeatedly adds new bids/asks into a persistent book, and stale best bid/ask levels can remain available.

This can magnify artificial spread capture across candles.

### Position Accounting

Severity: medium

Position accounting is mostly internally consistent for the current deterministic pair fills.

On buy fill:

```text
position += fillSize
cash -= fillPrice * fillSize
```

On sell fill:

```text
position -= fillSize
cash += fillPrice * fillSize
```

Because both buy and sell legs are guaranteed to fill, final position returns to zero.

But this does not model realistic one-leg risk, partial fills, cancel/fill races, or delayed responses.

### Cash Accounting

Severity: medium

Cash arithmetic is internally consistent for paired fills, and `EventDrivenBacktestResult.FinalPnL` correctly uses:

```text
ts.Cash - startingCash
```

However:

- event-driven cash excludes fees and slippage;
- cash profit comes from artificial crossed spreads;
- `TradingStrategy.Realized` is set to total cash when flat, which is semantically wrong if starting cash is non-zero.

The reports use `FinalPnL`, so the displayed event-driven PnL is cash-delta based. Still, `TradingStrategy.Realized` should not be treated as realized PnL in this mode.

### OMS Duplicate Fills

Severity: medium

The current simulator should not create duplicate fills for the same order:

- `MarketSimulator.FillAllOrders()` copies open orders;
- deletes each order from `s.orders`;
- emits one fill response per order.

But `OrderManager.ProcessMarketResponse()` forwards every market response to the strategy and does not enforce idempotency. If a duplicate `FILLED` response is injected by a future gateway/simulator, the strategy could process it again.

Conclusion: duplicate fills are not generated by the current simulator, but the OMS is not yet protected against duplicate market responses.

## Direct Answers

| Question | Answer |
|---|---|
| Why is `pnlDiff=2252.38` large? | Because event-driven PnL is dominated by artificial crossed-book spread capture, while for-loop PnL comes from candle signal fills with fees/slippage. |
| Are event-driven fills realistic? | No. They are deterministic full fills at submitted prices. |
| Does crossed-book simulation create artificial profit? | Yes. It is designed to create arbitrage opportunities. |
| Does position accounting match? | Mostly yes for guaranteed paired fills; it does not model one-leg or partial-fill risk. |
| Does cash accounting match? | Arithmetic cash changes are consistent, but omit costs and rely on artificial spread capture. |
| Can OMS lifecycle create duplicate fills? | Current simulator does not, but OMS lacks idempotency if duplicate fill responses are injected. |

## Recommendation

Treat Chapter 9D/9E event-driven PnL as a **system validation metric only**.

Do not use event-driven PnL as strategy performance until these are addressed:

- remove artificial crossed-book generation for performance tests;
- reset, consume, or expire order-book liquidity;
- add fees and slippage to event-driven fills;
- add fill ratio and partial fills;
- add latency and response scheduling;
- add OMS response idempotency;
- model one-leg risk for paired orders;
- separate system-flow tests from performance backtests.

The current event-driven harness is still valuable. It proves the queue path and OMS/simulator lifecycle are alive. It just should not be interpreted as alpha.
